The three MVP tables with their constraints and RLS. T03's SQL functions build on this.

**Done**

- Migration `supabase/migrations/20261006031429_schema.sql`: enums `unit_type` (count, minutes)
  and `challenge_status` (active, completed, abandoned); tables `profiles`, `challenges`,
  `daily_entries`; grants; RLS on all three.
- pgTAP: `supabase/tests/profiles.test.sql` (17), `challenges.test.sql` (18),
  `daily_entries.test.sql` (19), plus the existing smoke test (1): 55 tests.

**Decisions**

- **Timezone validated by a `BEFORE INSERT OR UPDATE OF timezone` trigger against
  `pg_timezone_names`**: CHECK needs an immutable expression and the tz catalog isn't one. Marking a
  lookup function `IMMUTABLE` would be a lie that breaks on tzdata updates and dump/restore. The
  trigger lets `NULL` through so the `NOT NULL` constraint reports it (23502). Invalid names raise
  22023.
- **`user_id` ownership enforced by a composite FK** `(challenge_id, user_id) → challenges(id,
  user_id)` with `unique (id, user_id)` on `challenges`: an entry can't belong to a user other than
  the challenge owner, even when written by a `security definer` function. That FK also covers
  "challenge exists", so there is no separate `challenge_id` FK.
- **`daily_entries.user_id` is denormalized** (it's derivable from the challenge) so the
  one-running-timer partial unique index and the RLS policy work on one table without a join.
- **Cascades**: `auth.users → profiles → challenges → daily_entries`, all `on delete cascade`.
  Deleting an account removes its data. `challenges.user_id` references `profiles` (per the data
  model), not `auth.users`, so a challenge always has a timezone to compute days with.
- **Start from zero privileges**: `revoke all` from `anon` and `authenticated` on all three tables,
  then grant back only what's needed. Supabase's default privileges grant `ALL` to both roles.
  RLS alone wouldn't block a client `UPDATE` on `daily_entries` if the grant existed and a
  policy were later added by mistake.
- **Column-level grants** for insert/update. `profiles`: insert `(id, display_name, timezone)`,
  update `(display_name, timezone)`. `challenges`: insert `(user_id, action, unit_type,
  start_date)`, update `(action, status)`. This keeps `id`, `user_id`, `created_at`, `unit_type`
  and `start_date` from changing after insert. `WITH CHECK` alone would allow e.g. re-pointing a
  challenge's `id` or moving `start_date` back to inflate the day count.
- **`daily_entries`: `SELECT` only** for `authenticated`. All writes go through T03's functions
  (invariant 1). No `DELETE` grant on any table, so history can't be erased from the client.
- **Policies use `(select auth.uid())`** rather than bare `auth.uid()`: Postgres evaluates it once
  per statement instead of once per row (Supabase's RLS performance guidance).
- **`action` non-blank check is `action ~ '[^[:space:]]'`**: rejects tabs and newlines too, not
  only spaces.
- **Index on `challenges(user_id)`**: RLS filters every challenges query by it. `daily_entries`
  needs no extra index: `(challenge_id, entry_date)` is unique-indexed, and the partial index
  covers running timers.
- **No profile auto-creation trigger on `auth.users`**: the timezone is captured at sign-up by the
  client (FR10), and changing the auth flow is out of scope here.

**Open for T03 / owner**

- `challenges.start_date` is client-supplied on insert. Invariant 5 says day boundaries come from
  SQL, not the client clock. A `create_challenge` function (or a default from the profile's
  timezone) in T03 can close this. After that, the insert grant can be revoked.
- `challenges.status` is client-updatable (needed to abandon a goal). Setting `completed` from the
  client is therefore possible. If it should only follow from 100 completed days, T03 should
  narrow it.
